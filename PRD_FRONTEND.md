# PRD: Фронтенд «Умный кредитный кабинет» (миграция со Streamlit на Next.js)

Версия: 1.0 · Дата: 2026-10-23 · Статус: черновик на согласовании

---

## 1. Контекст

Проект — прототип «цифрового кредитного конвейера» для малого бизнеса (хакатон «Альфа-Будущее 2026», кейс «Умный кредитный кабинет»). Бэкенд готов: FastAPI (`main.py`, порт 5555) + SQLite, LLM-ассистент, конвейер скоринга, АРМ для сотрудников банка. Фронтенд сейчас — Streamlit (`frontend/app.py`, ~2300 строк), что не соответствует ни критериям UX жюри, ни требованию «работающий прототип продукта, а не набор экранов».

Цель — заменить Streamlit-фронтенд на полноценное SPA на стеке, принятом в проектах piratepress/piratepitch (Next.js 16 + React 19 + FSD), с айдентикой Альфа-Банка, покрыв весь функционал текущего фронтенда и контракт API из `~/HakatonChat/files/FRONTEND_GUIDE (1).md` (актуальная версия; старый `FRONTEND_GUIDE.md` игнорировать).

## 2. Цели и критерии успеха

| Цель | Как измеряем |
|---|---|
| Работающий веб-прототип, проходящий все 5 пользовательских сценариев из ТЗ | Каждый сценарий проходится end-to-end через UI без ручных запросов к API |
| Два интерфейса с общим состоянием: кабинет клиента + АРМ сотрудника | Решение аналитика в АРМ видно клиенту без перезахода (polling) |
| Айдентика Альфа-Банка | Цвета/шрифты/радиусы из токенов core-components и alfabank.ru (см. §6) |
| Воспроизводимый запуск одной командой | `docker compose up` поднимает backend + frontend; сценарий проверки в README |
| Соответствие ТЗ хакатона | Веб-интерфейс (не мобильное приложение), всё внутри продукта (без email/SMS), Docker, тестовые данные и учётки |

## 3. Scope

### В scope
- Полный перенос функционала Streamlit-фронтенда (см. §5) на новый стек.
- Новый UI по макету-концепту «Бизнес.Плюс» (`photos/photo_9@19-10-2026_21-49-52.jpg`): левый сайдбар, центральный чат, правая панель с вкладками.
- Айдентика Альфа-Банка поверх концепта.
- Адаптивная вёрстка (desktop-first; планшет/мобильный — базовая пригодность, mobile app не требуется и запрещён ТЗ как формат сдачи, но адаптивная вёрстка не возбраняется).
- Docker-сборка фронтенда, обновление docker-compose.
- Страница входа/регистрации, восстановление сессии после перезагрузки.

### Вне scope
- Изменения бэкенда (кроме точечных: CORS не нужен — прокси через Next rewrites; см. §9).
- Стриминг LLM-ответов (SSE/WebSocket) — API отдаёт ответ целиком; эмуляция «печатает» на клиенте.
- Загрузка файлов на сервер — по контракту на бэкенд уходят только имена файлов (файлы сохраняются локально в `uploads/{inn}/` — в SPA это моделируется, см. §5.4).
- i18n (только русский), тёмная тема (макет и айдентика Альфа — светлые; тёмная тема — опциональный stretch).
- Регистрация настоящей ЭП, интеграция с реальными ЕГРЮЛ/БКИ/ФНС — всё моки, как в ТЗ.

## 4. Стек и архитектура фронтенда

Копируется с piratepitch (ближе по типу: кабинет + поллинг) с дополнениями из piratepress.

### 4.1. Базовый стек
- **Next.js 16.3.1** (App Router, `reactCompiler: true`, `distDir: 'dist'`), **React 19.2.8**, **TypeScript 5**, пакетный менеджер **Bun**.
- **Tailwind CSS v4** (конфигурация через CSS `@theme`, без `tailwind.config`), `tw-animate-css`.
- UI-примитивы: **shadcn-паттерн на @base-ui/react** (button, card, dialog, input, select, tabs, tooltip, badge, skeleton, checkbox…), `cn()` из `clsx` + `tailwind-merge` + `class-variance-authority`.
- Иконки: **lucide-react**. Анимации: **framer-motion 13**.
- Клиент-стейт: **zustand 5** (сессия, токен). Сервер-стейт: **@tanstack/react-query 5** (заявки, профиль, очередь АРМ) — берём из piratepress вместо ручного `use-poll` pitch; для автообновления — `refetchInterval` (АРМ: 15 с).
- HTTP: **ky v2** — единый инстанс `shared/api/http.ts` (Bearer из zustand, разлогин при 401, unwrap ошибок `{detail}`).
- Валидация контрактов: **zod 4**, схемы в `entities/*/model/schemas.ts` с нормализацией snake_case → camelCase (FastAPI отдаёт snake_case).
- Тосты: **sonner**. Markdown в ответах ассистента: компонент `shared/ui/markdown` (как в piratepress).
- Линтер/форматтер: **Biome 2.4.2** (2 пробела, single quotes, width 100, kebab-case файлы) — конфиг как в референсах.

### 4.2. Структура — FSD
Новый фронтенд живёт в директории **`front/`** в корне репозитория. Текущая Streamlit-версия остаётся в `frontend/` нетронутой как fallback для демо (из compose она убирается, см. §9).
```
front/
├── src/
│   ├── app/                  # тонкий роутинг Next (route groups: (auth), (client), (bank))
│   └── fsd/
│       ├── app/              # root-shell, providers, styles/globals.css
│       ├── pages/            # login, chat, applications, profile, admin-queue…
│       ├── widgets/          # chat-panel, product-panel, app-sidebar, application-card, admin-queue…
│       ├── features/         # auth, send-message, submit-application, offer-response, sign, request-info, assign-analyst, decision…
│       ├── entities/         # user, profile, product, application, conversation (типы + zod-схемы + api-методы)
│       └── shared/           # ui/, api/http.ts, lib/, config/
├── Dockerfile
└── components.json, biome.json, postcss.config.mjs
```

### 4.3. Связь с бэкендом
- Браузер ходит только на same-origin `/api/*`; **`rewrites()` в `next.config.ts` проксирует на `BACKEND_URL`** по pitch-паттерну (`/api/*` → `BACKEND_URL/api/*`) — пути бэкенда уже под `/api`, переименований не нужно.
- `BACKEND_URL` — Docker build-arg (rewrites запекаются в routes-manifest при сборке).
- CORS на бэкенде не нужен (same-origin для браузера).
- Токен: бессрочный opaque Bearer; хранение — in-memory zustand + persist в localStorage (для восстановления сессии; refresh-механики нет, при 401 — разлогин и редирект на вход).

## 5. Функциональные требования

### 5.1. Авторизация
- Страница с вкладками «Вход» / «Регистрация»; логин 3–64, пароль 4–128; при регистрации выбор роли: `client`, `bank_manager`, `bank_analyst`.
- После входа редирект по роли: `client` → кабинет (чат), банковские роли → АРМ.
- Восстановление сессии после перезагрузки: `GET /api/auth/me` → `GET /api/conversations` → история активного диалога → `GET /api/me/profile` → `GET /api/me/applications`.
- 401 на любом запросе → очистка сессии + редирект на вход.
- Защита от SQL-инъекций — на бэкенде; на фронте — обычная клиентская валидация форм.

### 5.2. Кабинет клиента (роль `client`)
Layout по макету-концепту: левый сайдбар (Главная, Кредиты, Заявки, Профиль, Поддержка + карточка «ИИ-ассистент»), центр — чат, справа — панель с вкладками «Рекомендуемые продукты / Мой профиль / Заявки».

**Чат с ИИ-ассистентом**
- Отправка: `POST /api/conversations/{id}/messages`. Медленная ручка — таймаут клиента ≥ 90 с, спиннер «Ассистент печатает…», блокировка повторной отправки до ответа.
- `reply` рендерится как **markdown**.
- `profile_updates` из ответа применяются к отображаемому профилю без перезагрузки.
- **Гейтинг рекомендаций**: карточки продуктов показываются только когда в ответе непустой `recommendations` (бэкенд отдаёт их после 5 заполненных полей профиля) или через кнопку «Подобрать продукты» (`POST /api/recommendations`), активную при заполненных обязательных полях (стаж, выручка, прибыль, сумма, срок). Подбор «в обход диалога» не делать.
- История диалогов в сайдбаре, «Новая заявка» создаёт диалог (`POST /api/conversations`).

**Вкладка «Рекомендуемые продукты»**
- Карточки продуктов: название, тег «Лучший выбор» для первой рекомендации, сумма, срок, ставка, условие, кнопка «Выбрать»; «Сравнить все продукты» (таблица/модалка сравнения из `GET /api/products`).
- После выбора продукта — блок «Параметры заявки»: сумма/срок в диапазонах продукта, аннуитетный расчёт (`POST /api/profile/{id}/payment`): платёж, всего к возврату, переплата; дисклеймеры; чекбокс подтверждения.

**Модалка «Данные для заявки»** (обязательная, не закрывается по клику вне — аналог `@st.dialog(dismissible=False)`)
- Поле ИНН + кнопка «Заполнить по ИНН» → `GET /api/registry/{inn}` (мок-реестр; тестовые ИНН: 7701234567, 502712345678, 7812345678, 5024123456, 6150123456). Автозаполнение секции «О компании».
- Секции по анкете из ТЗ: о кредите, о компании, о руководителе, владельцы >25% (только ООО), о финансах, документы, 2 обязательных согласия (ПДн + кредитная история).
- **Документы**: выбор файлов (скан паспорта, устав/декларация) — в API уходят только имена файлов; реальная загрузка моделируется (файлы не покидают браузер, отображается список «прикреплённых»).
- Клиентская валидация по правилам `ClientDataRequest` (ИНН 10/12 цифр, телефон +7…, email, обязательные согласия) + показ `missing_fields` от бэкенда.

**Отправка заявки**
- Один клик: `POST /api/applications` (черновик) → `POST /api/applications/{id}/submit` (конвейер).
- Диалог «Заявка принята» с номером, метриками и подсказкой следующего шага.

**Вкладка «Заявки»** — карточки заявок со статусной моделью (14 статусов), русские метки (маппинг как `STATUS_LABELS` в текущем app.py). Действия по статусу:

| Статус | UI-действия |
|---|---|
| `draft` | «Отправить заявку»; редактирование суммы/срока (`PATCH /api/applications/{id}`) |
| `needs_info` | Причина (`needs_info_reason`/`missing_fields`) + «Обработать повторно» (`POST /scoring`) |
| `offer_ready` | Показ предложения (при `approved_with_changes` — скорректированные условия с визуальным diff); «Принять» / «Отклонить» (с обязательным полем причины) → `POST /offer-response` |
| `accepted` | «Подписать договор» (`POST /sign`, ЭП моделируется) |
| `rejected` | Стоп-факторы (без показа балла клиенту), альтернативные продукты из `decision_details.alternatives` + «Оформить заявку» на альтернативу (новый черновик) |
| `issued` | Финальный экран «Кредит выдан» |
| при любом решении | «Объяснить решение (ИИ)» (`POST /explain`, `audience=client`; медленная ручка — спиннер) |

- Автосинхронизация: react-query с `refetchInterval` ~10–15 с на `GET /api/me/applications` — решения банка видны без действий клиента.
- Балл скоринга клиенту **не показывать** (только банковским ролям).

**Вкладка «Мой профиль»** — поля профиля бизнеса (обновляемые из чата), форма редактирования через `PATCH /api/profile/{id}`.

### 5.3. АРМ сотрудника банка (роли `bank_manager`, `bank_analyst`)
- Очередь всех заявок: `GET /api/admin/applications?status=…` с фильтром по статусу, автообновление 15 с + кнопка «Обновить».
- Карточка заявки: параметры, клиент с ИНН, анкетные данные (`client_data`), разбор факторов скоринга, балл, история статусов (`GET /history`).
- Действия менеджера (`data_check` / `scoring` / `manual_review`): «Запросить уточнения» (текст 3–1000, `POST /request-info`), «Передать аналитику» (`POST /assign-analyst`).
- Действия аналитика (`manual_review`): решение `approved` / `approved_with_changes` / `rejected` + обязательная причина (`POST /decision`); «Объяснить решение (ИИ)» с `audience=analyst`.
- Для остальных статусов — подсказка «действия не требуются» (как `ADMIN_NO_ACTION_HINTS`).
- 403 при попытке действия не своей роли — обработка с понятным сообщением.

### 5.4. Общее
- Единая обработка ошибок API: тост (sonner) с текстом из `{detail}`, 422 — подсветка полей формы.
- Скелетоны на первичных загрузках; оптимистичные апдейты там, где безопасно (отправка сообщения — пузырь пользователя сразу).
- Все суммы — форматирование «3 000 000 ₽», ставки «16,5 %».

## 7. API-контракт (потребляемые эндпоинты)

Бэкенд не меняется. Полный список — 27 эндпоинтов: auth (3), conversations (4), profile (6), recommendations (1), applications (9), admin (3), registry (1), products (1) — см. `FRONTEND_GUIDE (1).md` и `main.py`. Zod-схемы пишутся по `src/schemas/*` бэкенда. Известные особенности:
- `/api/recommendations`, `/api/products`, `/api/registry/{inn}` — без авторизации (осознанно, для демо).
- Ответ заявки включает `score`, `decision_details`, `client_data` — клиентскую часть фильтруем в UI (без балла), банковскую — показываем полностью.
- Ошибки: FastAPI `{detail}` (строка или массив 422) — нормализуем в `shared/api/http.ts`.

## 8. Нефункциональные требования

- **Производительность**: первая отрисовка кабинета < 2 с на обычном ПК; чат — без перерендера всей страницы (React Compiler + мемоизация списка сообщений).
- **Надёжность UX**: двойная отправка сообщения/заявки заблокирована; обрыв запроса — понятная ошибка и возможность повторить; состояние чата не теряется при переходе по вкладкам.
- **Безопасность**: токен только в Bearer-заголовке (не в URL/логах); рендер markdown без `dangerouslySetInnerHTML` с сырым HTML (санитизация); ролевая маршрутизация (middleware/route guards).
- **Совместимость**: последние Chrome/Firefox/Safari; desktop ≥ 1280px в первую очередь.
- **Фиксация версий**: `bun.lock` в репозитории; Node/Bun версии пинятся в Dockerfile.

## 10. Тестовые сценарии (приёмка)

Проходятся в UI на docker-compose окружении с синтетическими данными:

1. **Быстрое автоодобрение** — ООО «Северная пекарня» (ИНН 7701234567), 3 млн ₽ / 12 мес: чат → рекомендации → модалка → автозаполнение по ИНН → отправка → статус доходит до `offer_ready` → принятие → подписание → `issued`.
2. **Дозагрузка документа** — ИП Петров: заявка уходит в `needs_info`, клиент видит причину, дозагружает (моделирует) документ, «Обработать повторно» → одобрение.
3. **Альтернативные условия** — «Городская логистика»: запрошенная сумма больше возможной → `offer_ready` с `approved_with_changes` (6 млн/12 мес или 10 млн/24 мес) → клиент принимает скорректированное предложение.
4. **Ручная экспертиза** — «ЭкоПласт»: `manual_review` → менеджер передаёт аналитику → аналитик выносит решение с причиной → клиент видит результат и объяснение ИИ.
5. **Отказ с причиной** — «Ремстрой-Юг» (налоговый долг): `rejected`, клиент видит понятную причину и альтернативы, может оформить заявку на альтернативный продукт.

Плюс сквозные проверки: восстановление сессии после F5; решение аналитика появляется у клиента без перезахода; 401 → разлогин; 403 в АРМ при действии не своей роли.

## 11. Риски и открытые вопросы

| Риск / вопрос | Влияние | Предложение |
|---|---|---|
| ТЗ требует LLM **с открытыми весами**, бэкенд использует YandexGPT | Критерий жюри | Поднять в команде; фронтенду безразлично, но фиксируем в THIRD_PARTY_NOTICES |
| Swagger UI на бэкенде отключён, а ТЗ требует OpenAPI/Swagger | Артефакт сдачи | Задача на бэкенд (вне scope фронтенда), зафиксировать в роадмапе |
| Шрифт Alfa Interface Sans с CDN — зависимость от сети | Независимость от платных/внешних ресурсов | Скачать woff2 в `public/fonts`, зафиксировать лицензионную оговорку в THIRD_PARTY_NOTICES |
| Загрузка файлов: бэкенд принимает только имена | Реалистичность демо | Файлы не покидают браузер; UI показывает «прикреплено». В README явно описать упрощение (ТЗ разрешает) |
| Медленные LLM-ручки (60+ с) без стриминга | UX | Спиннеры + поясняющие тексты; таймаут ky 120 с |
| Порт 8502 может быть занят локально | Dev-окружение | Переопределяется переменной `FRONTEND_PORT` в compose |

## 12. План работ (этапы)

1. **Скелет**: init Next.js-проекта по шаблону piratepitch (Bun, Tailwind v4, Biome, FSD, ky-инстанс, zustand-сессия, rewrites-прокси). Альфа-токены в `@theme`, шрифты локально.
2. **Авторизация + гарды**: страницы входа/регистрации, восстановление сессии, редиректы по ролям.
3. **Чат**: виджет диалога, markdown, спиннеры, гейтинг рекомендаций, история диалогов, применение `profile_updates`.
4. **Продукты и заявка**: панель рекомендаций, параметры + расчёт платежа, модалка анкеты с автозаполнением по ИНН и валидацией, отправка заявки.
5. **Кабинет заявок**: карточки со статусной моделью, все действия по статусам, explain, альтернативы, автосинхронизация.
6. **АРМ**: очередь с фильтрами и автообновлением, действия менеджера/аналитика, разбор факторов и история.
7. **Полировка**: skeletons, тосты, анимации framer-motion, адаптив, empty states.
8. **Инфраструктура**: Dockerfile, compose, README (сценарии проверки, учётки), THIRD_PARTY_NOTICES, проход 5 приёмочных сценариев.

Оценка: этапы 1–6 — ядро (must-have к дедлайну онлайн-тура 26.10), этапы 7–8 — по остаточному принципу, но README и тестовые данные обязательны (критерий «Готовность к проверке»).
